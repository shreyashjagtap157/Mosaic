# Mosaic-µ Converged Implementation Plan

Status: active implementation plan  
Date: 2026-08-07

## 1. Objective

Implement Mosaic as a small Rust tokenization microkernel and reference semantics with exact byte identity, deterministic pack execution, generated Unicode data, model/consumer projections, and later modular language/domain support. Development must falsify weak assumptions early rather than maximize feature count.

## 2. Build philosophy

1. **Correctness oracle first.** Every optimized path answers to an intentionally simple reference implementation.
2. **Source truth first.** Byte coordinates and exact reconstruction precede Unicode, language, model, or compiler semantics.
3. **Offline generation, online execution.** UCD compilation, vocabulary training, automata construction, minimization, and pack optimization stay outside deployed runtime crates.
4. **Reproducibility is data identity.** Canonical manifests and pack payloads are content-addressed and deterministic.
5. **No speculative performance machinery.** Scanner VM, semantic-aware CDC, rich graphs, GPU execution, and native byte-patch models are deferred until a measured use case earns them.
6. **Product wedge is empirical.** M4 runs a time-boxed Wedge Tournament; investment order branches after results.

## 3. Repository architecture

```text
mosaic/
├── Cargo.toml
├── rust-toolchain.toml
├── crates/
│   ├── mosaic-core/        # no_std byte substrate, source coordinates, leaves
│   ├── mosaic-ir/          # minimal Core IR now; richer IR later
│   ├── mosaic-reference/   # simple correctness oracle
│   ├── mosaic-engine/      # production-oriented executor
│   └── mosaic-pack/        # pack schema/checked reader/verifier
├── docs/
│   ├── spec/
│   ├── implementation/
│   └── adr/
├── fixtures/packs/         # canonical pack regression fixtures
├── fuzz/                   # cargo-fuzz targets, excluded from workspace
├── benches/                # benchmark manifests/results later
├── tools/                  # deterministic dev/build/validation tools
└── .github/workflows/      # PR/nightly/release CI tiers
```

Additional crates are added only when their dependency boundary is justified. Planned later crates include `mosaic-unicode`, `mosaic-language`, `mosaic-lex`, `mosaic-model`, `mosaic-document`, `mosaic-store`, `mosaic-ffi`, `mosaic-cli`, and offline `mosaic-build`/`mosaic-train` tools.

## 4. Milestone dependency graph

### M0 — Engineering substrate

Deliver repository structure, CI topology, benchmark contract, fuzz skeleton, ADR framework, reference-hardware policy, unsafe-code tracking, and deterministic empty-pack fixture.

Exit gates:

- repository validator passes;
- documentation and ADR structure exists;
- fixture generator produces byte-identical output across repeated local runs;
- PR/nightly/release workflows are declared;
- Rust compilation gates are documented and become mandatory once toolchain is available.

### M1 — Exact source substrate

Deliver `mosaic-core`, minimal `mosaic-ir`, independent byte reference/engine projections.

Normative result:

```text
source length N
→ exactly N conceptual byte leaves
→ leaf i maps to [i, i+1)
```

Physical allocation of a leaf array is forbidden as a required representation.

Exit gates:

- every possible byte value round-trips;
- arbitrary generated byte buffers round-trip;
- range arithmetic is checked;
- canonical leaves are pack-independent;
- `mosaic-core` builds with `no_std` and without allocation;
- reference and engine byte projections match exactly.

### M2 — Deterministic pack executor

Deliver checked pack container, exact identity, dependency lock graph, DFA executor, integer cost model, total path ordering, manifest identity.

Exit gates:

- malformed packs fail closed;
- all offsets/lengths/targets are checked;
- canonical empty/test packs rebuild byte-identically cross-platform;
- canonical execution rejects unresolved dependencies;
- deterministic cost/path test vectors pass.

### M3 — Unicode + static tokenizer

Deliver scalar Unicode oracle, generated compact pack runtime, BPE compatibility, candidate matcher, reference Viterbi, optimized Viterbi, IDs projection.

Exit gates:

- pinned Unicode conformance passes;
- scalar/generated output is identical;
- reference/optimized segmentation is identical;
- exact compatible BPE projections match their declared model semantics;
- IDs-only throughput reaches at least the 70% floor against a semantics-equivalent strong baseline after profiling.

### M4 — Wedge Tournament

Use the frozen M3 substrate. Implement only thin experimental adapters. Run multilingual LLM, compiler+LLM, and assurance-SDK candidates in parallel. Allow `NONE` as a result.

Output `WEDGE-EVAL-001` and select M5 branch.

### M5 branches

- **M5A:** language packs/routing if multilingual LLM wins.
- **M5B:** compiler profiles/shared source processing if compiler+LLM wins.
- **M5C:** trust/security/SDK integration if assurance wins.
- **M5H:** explicitly approved hybrid only if constituent wedges pass independently and hybrid engineering/value gates pass.

### M6-M8

Incrementality and streaming hardening, rich/shared platform expansion, then security/SIMD/packing/cache hardening. Exact ordering inside M6-M8 follows the selected wedge.

## 5. Reference-versus-engine contract

`mosaic-reference` MUST be:

- scalar;
- single-threaded;
- obvious rather than clever;
- independent of production matcher/table expansions;
- permitted to allocate for clarity;
- used as the canonical semantic oracle in differential tests.

It MUST NOT add SIMD, JIT, content-defined chunking, double-array expansion, speculative caching, or architecture-specific shortcuts.

`mosaic-engine` MAY optimize representation and execution but must satisfy MOS-REQ-023 against reference semantics.

## 6. Deterministic arithmetic

- edge costs: `i32`;
- path accumulator: checked `i64`;
- floating-point canonical runtime path selection: forbidden;
- overflow: explicit error, never saturation/wrap;
- quantizer identity/version recorded by pack build metadata;
- tie ordering fixed by MOS-REQ-022 and exercised by adversarial equal-cost vectors.

Performance of checked arithmetic is benchmarked at M3. If verifier-proven bounds allow safe unchecked internal arithmetic, any such optimization must reside in a reviewed unsafe/low-level module and remain differential-equivalent to checked reference behavior.

## 7. Pack design constraints

The canonical pack format is deliberately boring:

- fixed magic and format version;
- explicit little-endian integers;
- section directory with offsets and lengths;
- no raw pointers or Rust/native object serialization;
- checked readers over untrusted bytes;
- canonical section/string ordering;
- no uncontrolled timestamps or host paths in hashed payload;
- content hash as exact identity;
- signatures are trust metadata, not a substitute for structural validation.

M0 contains a minimal test fixture; M2 evolves it into the first executable deterministic pack format.

## 8. Resource-limit model

Resource limits are split rather than put into one junk-drawer object:

- `PackValidationLimits`
- `RuntimeProcessingLimits`
- `ProjectionLimits`
- `SerializationLimits`

The eventual contract must bound at least source bytes, token bytes, candidates per position, normalization expansion, nesting, VM steps, blocks, graph edges, mapped pack bytes, dependency depth/fanout/count, section count/bytes, decompressed bytes, dictionaries, aliases, mapping fanout, language candidates, and detector models.

## 9. Testing strategy

Required families:

- property tests over arbitrary bytes/ranges;
- conformance vectors;
- reference-versus-engine differential;
- scalar-versus-SIMD differential later;
- full-versus-streaming differential;
- full-versus-incremental differential;
- pack build reproducibility;
- malicious pack corpus;
- fuzz regression corpus;
- cross-platform golden vectors;
- FFI ownership/lifetime tests once FFI exists.

No optimization is accepted on benchmark result alone.

## 10. Benchmark families

B1 **Compatibility:** identical vocabulary/rules to baseline; measures implementation overhead.  
B2 **Greenfield:** equal corpus/vocabulary budgets; compares segmentation algorithms.  
B3 **Shared pipeline:** measures time/memory from input arrival until all declared consumers are ready.  
B4 **Quality-adjusted downstream:** fixes model/data/compute and measures quality per compute/context cost.

Public performance claims require machine, corpus, build, manifest, thread count, output density, and warm/cold state in the benchmark artifact.

## 11. Deferred features

The following are intentionally not M0-M3 requirements unless evidence forces them earlier:

- scanner VM;
- semantic-aware content-defined chunking;
- full rich Token IR graph;
- remote registry governance;
- automatic span-level language detection;
- GPU tokenization;
- dynamic/native byte-patch LLM architecture;
- large language catalog;
- extensive bindings.

The project wins by removing invalid complexity early, not by creating an impressive directory count.
